# 法院文书下载器 · 自有服务器自动同步

## 这是干什么的

把「exe + 更新元数据同步到自有服务器」这一步**从人工变成自动**。

### 为什么需要它

2026-10-08 出过一次事故：`release_all.py` 发完 v2.10.1 后，GitHub 上一切正常
（Release 齐全、签名通过、下载链接可下），但**自有服务器的 `updates/court.json`
还停在更早版本**。

后果：官网的下载按钮**优先走自有服务器直链**（不翻 GitHub），所以从官网点下载
拿到的是**旧版 exe**；客户端检查更新时从「备用源」读到的也是旧版本号。

这个缺口**不会报任何错** —— 发版脚本全绿，只有真实用户会中招。所以现在
`release_all.py` 发完会**主动拉线上元数据比对版本号**，没跟上就直接警告。

## 一、部署（只需做一次）

### 1. 把脚本传到服务器网站根目录

`web/update_site.py` 就是服务器端脚本，把它放到**网站根目录**（和 `index.html` 同级）：

```
/www/wwwroot/你的站点目录/
├── index.html
├── update_site.py        ← 本脚本
├── updates/
│   └── court.json        ← 脚本自动写
└── files/                ← 脚本自动建，双 exe 放这里
```

传到服务器的三个办法（任选其一）：

- **宝塔面板** → 文件 → 进入网站目录 → 上传
- 已配好 SSH 的话（本项目沙箱里 ssh.exe 会被拦，用面板最省事）：
  `scp web/update_site.py root@<服务器>:/www/wwwroot/你的站点目录/`
- 或者把脚本内容复制粘贴新建文件（脚本只用标准库，无编码陷阱）

### 2. 加一条计划任务（这才是「自动」的关键）

宝塔面板 → **计划任务** → 添加任务：

| 项 | 填什么 |
|---|---|
| 任务类型 | Shell 脚本 |
| 脚本内容 | `python3 /www/wwwroot/你的站点目录/update_site.py` |
| 执行周期 | 想立刻同步一次就选「一次」点执行；想以后自动跟上就选「N 小时」或每天 |

服务器自带 python3 即可，**不需要装任何包**（脚本只用标准库）。

### 3. 立刻同步一次

在计划任务里点「执行」，日志里应该看到：

```
GitHub 最新：v2.10.2（…）
绿色版资产：CourtDocDownloader_v2.10.2.exe    安装版：CourtDocDownloader_v2.10.2_setup.exe
  CourtDocDownloader_v2.10.2.exe           下载成功（30.6 MB，https://ghfast.top/）
  CourtDocDownloader_v2.10.2_setup.exe     下载成功（32.1 MB，https://ghfast.top/）
已写入 …/updates/court.json（v2.10.2，3.1 KB）
本站已从 v2.10.1 同步到 v2.10.2
```

看到 `本站已从 vX 同步到 vY` 就成功了。

## 二、日常用法

配好计划任务后，**发版不需要做任何事** —— 下次发完版，服务器会在下一个周期自动跟上。

想立刻同步（比如刚发完版想马上验证）：

```bash
# 只看线上最新版，不写任何文件（安全探测）
python3 update_site.py --check

# 立刻同步
python3 update_site.py

# files/ 里保留最近 3 个版本的 exe（默认 2）
python3 update_site.py --keep 3
```

### 脚本做了什么

1. 查 GitHub 最新 Release，取版本号与资产清单
2. 把绿色版 + 安装版 exe 镜像到 `files/`（多源容灾，自动切加速镜像）
3. 写 `updates/court.json`（含 sha256、下载地址、更新说明）
4. 清理 `files/` 里超过保留份数的旧版 exe

### 关键的安全设计

| 措施 | 防什么 |
|---|---|
| **先下 exe，成功后才写元数据** | 用户不会点到一个「已更新但文件还不存在」的链接 |
| **大小校验 + MZ 头校验** | 国内直连 GitHub 常中途断流，实测会「成功」下到 604KB 残包（声明 32MB）。只判 HTTP 200 会把残包镜像上去，用户拿到打不开的 exe |
| **sha256 自己算** | GitHub API 的资产摘要常年是 `null`，填错会让**所有用户更新失败**（客户端会拿它校验） |
| **原子写入 + 自动备份** | 写到一半断电不会留下半个 json 把站点搞挂 |
| **幂等** | 内容没变就跳过，可安全地频繁执行（计划任务每小时跑也不会重复下载） |
| **镜像优先，直连放最后** | 国内服务器直连 GitHub 实测会白等 3 分钟才失败；镜像站 30.6MB 约 20 秒下完 |
| **只删符合命名规则的旧版 exe** | 不会误删你手动放上去的其他文件 |

## 三、验证是否真的生效

```bash
# 1. 看线上元数据版本号
curl http://<你的站点>/updates/court.json | head -c 200

# 2. 看 exe 能不能下（期望 200 或 206）
curl -I http://<你的站点>/files/CourtDocDownloader_vX.Y.Z.exe

# 3. 比对 sha256 与 GitHub 上的产物是否一致
sha256sum files/CourtDocDownloader_vX.Y.Z.exe
#    与更新弹窗 / court.json 里的 sha256 对得上
```

`release_all.py` 也会在发版末尾自动核对第 1 步，没跟上会直接警告。

## 四、常见问题

**Q：计划任务日志报 `ModuleNotFoundError`？**
A: 不会 —— 脚本只用 Python 3 标准库。若报 `python3: command not found`，
宝塔里改成绝对路径 `/usr/bin/python3` 或 `/www/server/python3/bin/python3`。

**Q：下载很慢？**
A: 脚本默认走加速镜像（实测 30.6MB 约 20 秒）。想指定别的源：
`python3 update_site.py --exe-prefix https://你的镜像/`

**Q：exe 没下下来，但元数据更新了？**
A: 不会 —— 绿色版下失败时脚本会直接中止、**不写元数据**。这是有意设计：
宁可元数据停在旧版（用户拿到旧但完整的 exe），也不能让用户点到坏文件。

**Q：磁盘满了怎么办？**
A: `--keep 1` 只留最近 1 个版本（双 exe ≈ 64MB）。

**Q：能不能改成 SSH 从本机推？**
A: 可以，但没必要。服务器主动拉 GitHub 的方式：不需要在发版机上保存服务器密码、
不怕沙箱拦 ssh、也不怕本机不在场。发票识别汇总工具用的就是这个思路
（`InvoiceOcrTool/deploy/update_site.py`）。
